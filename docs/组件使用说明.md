## 2. idempotent 接入：MQ 消费幂等迁移（2026-11-15）

**为什么**：原 `AbstractIdempotentConsumer` 以 `event_consume` 表 `(consumer_group, event_id)` 先插行去重——**业务失败后行已落库，MQ 重投被当「重复事件」跳过，失败事件永不重试**（首次失败即 at-most-once）。starsite-idempotent 的语义恰好修复：FAILED **释放键**，重投可重执行。

**迁移方式**：公开 API（`consumeIdempotent` 两重载）与 mq-consume-digest 日志格式零变化；构造器 `JdbcTemplate` → `IdempotentClient`；表由 `idempotent_record` 接管（`docker/mysql-init/22-idempotent.sql`；组件构造期 initDdl 自动建表，event_consume 保留存量数据）。

**组件四态 → 消费语义**：

| 组件结局 | 消费行为 | digest 状态 |
|---|---|---|
| EXECUTED | 执行 doConsume | success |
| REPLAYED | 窗口内重复，零执行跳过 | duplicate |
| FAILED（doConsume 抛异常） | 组件释放键后原样上抛交 MQ 重试；**重投重执行（修复点）** | error |
| CONFLICT / FAILED（目睹他方） | 上抛交 MQ 稍后重投（勿 ACK——首执行可能仍在飞） | error |

**声明式 `@StarsiteIdempotent` 适用条件**（暂无 backend 用例，预留）：需客户端请求号（Stripe Idempotency-Key 模式），典型如前端发起退款时携带 refundRequestNo。**不适用反例**：登录/注册（顺序重复应报业务错而非回放首次成功）、upsert 类（顺序重复应更新而非回放旧结果）、订单 CLOSED 重开（回放旧单破坏重开语义）——这类场景用**锁**保语义（见 §3）。

## 3. 并发防护用锁不用幂等的两个新用例（2026-11-15）

| 用例 | 锁名 | 防护 |
|---|---|---|
| payment 退款 `POST /api/payment/refunds` | `payment-refund:{orderId}` | 并发双击串行化（退款是资金动作，无 uk 兜底）；顺序级防重需前端请求号（未来可换 @StarsiteIdempotent） |
| family 建家庭 `POST /api/family` | `family-create:{ownerMemberId}` | count-then-insert 且 family 表无 uk，并发双击落两个家庭（不可恢复）；顺序重复仍走 4005 业务语义 |

**锁在控制器层而非 service 层的原因**：两个 service 方法都是 `@Transactional`——锁在事务方法内 `finally` 释放会留出「事务提交前窗口」，并发方在窗口期读到未提交的旧状态（旧订单状态/countByOwner=0）绕过校验。控制器层获取/释放，锁生命周期完整覆盖事务提交。

| 服务 | 配置 |

| family | lock mysql（建家庭并发锁） |
| health | async-command enabled/admin-token（STAR_ASYNC_ENABLED 兼容映射） |
| bench | sequence/async-command/lock 全 mysql（压测）；Hikari 20 |

| 其余服务 | 未显式配置（组件默认：lock/idempotent auto→jdbc 随服务 DataSource 生效；async-command 默认启用） |

## 5. 组件接入指南

1. **依赖**：业务模块一般无需声明——`star-site-common` 已传递 sequence/async/lock/idempotent 四族；schedule 按需在任务所在模块声明 starter 0.2.3。
2. **构件来源**：CI/镜像内构建走 `docker/maven-settings.xml` 的 m2-local 预置仓库；本机构建走宿主 `~/.m2`。**新组件预置流程**：组件仓 `mvn install` → 把 `{artifact}/{version}/` 下的 jar+pom 复制进 `docker/m2-local/com/xp/starsite/`（提交入库）与宿主 `~/.m2/repository` 对应目录。未发布线（如 0.2.3 的 schedule/idempotent）以此方式本地预置是既有实践（schedule 0.2.3 先例）。
3. **建表**：lock/async-command/schedule/idempotent 的表构造期 initDdl 自动创建（IF NOT EXISTS）；生产迁移脚本制时用 `docker/mysql-init/`（18-async-command.sql、22-idempotent.sql 等，幂等可并存）。
4. **新定时任务**：优先 `@StarsiteScheduled`（恰一执行+流水+错过策略开箱即用），勿再写 @Scheduled+手工锁样板；本服务无原生 @Scheduled 后可移除 `@EnableScheduling`（组件自带触发引擎，reminder/finance 已移除）。
5. **版本纪律**：全线统一 0.2.3。组件间有传递依赖耦合（schedule→lock、idempotent-starter→sequence-starter），**禁止混版**——升级时全族一起升并同步 m2-local。
   ⚠️ **当前 0.2.3 的实际身份**：组件仓 0.2.3 版本线在发布（2026-10-31）后仍在同版本号上继续交付（idempotent/quota/tuner 落地 + sequence 分包重构 `allocator.mysql`/`generator`/`facade`）。backend 与 m2-local 的 0.2.3 构件均为 **2026-11-14 未发布线构建**（同号覆盖，宿主 `~/.m2` 与 `docker/m2-local` 已同步一致）；10-31 发布版已被覆盖。待组件仓正式发版（0.2.4/0.3.0）时应全量升版并重新同步两处仓库。
